# Контент слайдов — определение формата

Этот файл задаёт формат `08-slide-content.md` — файла под конкретный проект, который служит **единственным источником истины** для контента слайдов. Сборщик дека (html-slide-deck-editor или pptx-скил) читает этот файл дословно. Без перефразирования, без переинтерпретации.

---

## Назначение

Контент слайдов фиксирует результат дистилляции (Gate 2b) в структурированном, читаемом сборщиком формате. Он отделяет **что говорить** (эта спецификация) от **как это выглядит** (визуальный стиль, тема, цвета, выбор визуализаций — отвечает сборщик дека на Gate 3).

**Ключевой инвариант:** перегенерация дека из того же файла спецификации даёт идентичный контент. Меняется только визуальная подача.

---

## Разделение ответственности

| Эта спецификация решает | Сборщик дека решает |
|---|---|
| Какой текст появляется на каждом слайде | Цвета, шрифты, размеры |
| Роли слайдов и логическую структуру | Какой тип визуализации использовать (бар, донат, прогресс) |
| Значения данных и их подписи | Как визуально отрендерить данные |
| Группировку контента (нумерованные точки) | Тип визуализации точек (карточки, панели, узлы, метрик-блоки) |
| Порядок слайдов | Переходы, анимации |
| | Контраст фона (светлый/тёмный) |

**Правило:** если речь о *что сообщить* — это в спецификации. Если о *как это выглядит* — это у сборщика.

## Структура файла

```markdown
# Slide Content Specification
<!-- Generated: {date} -->
<!-- Engagement: {client}/{project} -->
<!-- SINGLE SOURCE OF TRUTH — deck builder uses this verbatim -->

---

## Slide {N} — {Short Label}
- **Role**: {role}
- **Layout**: {layout}
- **Eyebrow**: {UPPERCASE LABEL}
- **Title**: {Action title — complete sentence stating key insight}
- {Content fields per slide type...}
- **Source**: {citation(s)}

---

## Slide {N+1} — {Short Label}
...
```

## Справочник полей

### Метаданные

| Поле | Обязательно | Значения | Заметки |
|-------|----------|--------|-------|
| **Role** | Да | См. ниже «Значения Role» | Объявляет назначение слайда — определяет выбор лэйаута и визуализаций сборщиком |
| **Layout** | Да | `hero`, `multi-col`, `split`, `full-width-stack`, `centered`, `step-flow`, `metric-row` | Структурная подсказка лэйаута сборщику |

### Контентные поля

| Поле спецификации | Что содержит | Заметки |
|------------|-----------------|-------|
| Eyebrow | Заглавная категория | например, «MARKET OPPORTUNITY» |
| Title | Action-title — полное предложение | Формулирует ключевой инсайт слайда |
| Hero Title | Многострочный display-текст | Строки как `- "text"` |
| Body Text | Абзац или список буллитов | Буллиты с префиксом `- ` |
| Point N | Нумерованная точка контента | Одна строка либо с вложенными под-точками (`  - detail`) |
| Callout Bar | Ключевой вывод | Одно предложение |
| Quote | Атрибутированная цитата | Под-поля: Text, Attribution |
| Source | Цитата(ы) источника | Строка-футер |

---

## Значения Role

| Role | Типичный Layout | Когда использовать |
|------|---------------|-------------|
| `cover` | hero | Открывающий слайд — заголовок, подзаголовок, брендинг |
| `section-divider` | hero | Разделяет крупные секции |
| `executive-summary` | full-width-stack | Обзор всего аргумента из 3–5 буллитов |
| `context` | full-width-stack или split | Бэкграунд, триггерное событие, цели |
| `argument` | multi-col или split | Один тезис с поддерживающими доказательствами |
| `comparison` | split | Две альтернативы рядом |
| `roadmap` | full-width-stack | Фазированное внедрение с таймлайном |
| `framework` | multi-col или step-flow | Опоры, операционная модель, архитектура |
| `deep-dive` | full-width-stack | Детализация в поддержку обзорного слайда |
| `metrics` | metric-row или multi-col | Количественный дашборд |
| `closing` | hero | Спасибо, следующие шаги, контакты |
| `appendix` | full-width-stack | Поддерживающие детали, методология, таблицы данных |

## Примеры по типам слайдов

### Cover

```markdown
## Slide 1 — Cover
- **Role**: cover
- **Layout**: hero
- **Eyebrow**: STRATEGIC REVIEW
- **Hero Title**:
  - "Будущее"
  - "цифровой коммерции"
- **Body Text**: Подготовлено для совета директоров | Март 2026
```

### Executive Summary

```markdown
## Slide 2 — Executive Summary
- **Role**: executive-summary
- **Layout**: full-width-stack
- **Eyebrow**: EXECUTIVE SUMMARY
- **Title**: Три стратегических сдвига откроют $200M новой выручки
- **Body Text** (bullets):
  - Сместить фокус GTM в enterprise — высший WTP, низший отток, в 3 раза LTV vs. SMB
  - Выйти в APAC раньше конкурентов — у топ-3 нет регионального присутствия
  - Свести цепочки поставок в одну сеть — снижение издержек на 15–20%
- **Callout Bar**: Цель: $200M дополнительной выручки к 2028
- **Source**: Внутренний анализ; McKinsey Digital Commerce Report 2025
```

### Argument (multi-col with points)

```markdown
## Slide 3 — Enterprise Drives Revenue
- **Role**: argument
- **Layout**: multi-col (3)
- **Eyebrow**: MARKET OPPORTUNITY
- **Title**: Enterprise-клиенты дают большую часть выручки и всю маржу
- **Point 1**: Доля выручки — 62% от общей даёт enterprise
- **Point 2**: Net retention — 118% enterprise vs. 94% SMB
- **Point 3**: Валовая маржа — 78% enterprise vs. 45% SMB
- **Callout Bar**: Enterprise = высший LTV и низшая стоимость привлечения
- **Source**: Сегментный анализ FY2025
```

### Comparison (split with points)

```markdown
## Slide 4 — Competitive Landscape
- **Role**: comparison
- **Layout**: split
- **Eyebrow**: COMPETITIVE POSITION
- **Title**: Никто из инкумбентов не закрыл рынок — окно открыто
- **Point 1**: Текущие игроки — топ-3 держат 28% совокупной доли, доминанта нет
  - На рынке и растут, но фрагментированы
- **Point 2**: Наша позиция — преимущество первого хода в APAC
  - У топ-3 нет значимого присутствия в APAC
- **Source**: Конкурентный мониторинг Q4 2025
```

### Roadmap (full-width-stack with points)

```markdown
## Slide 5 — Implementation Roadmap
- **Role**: roadmap
- **Layout**: full-width-stack
- **Eyebrow**: IMPLEMENTATION
- **Title**: Три фазы за 18 месяцев, старт с GTM в enterprise в Q2
- **Point 1**: Enterprise GTM — Q2–Q3 2026 | Найм VP Sales, сборка enterprise-пайпа, закрытие 5 якорных клиентов
- **Point 2**: APAC Expansion — Q4 2026 — Q1 2027 | Офис в Сингапуре, 3 локальных партнёрства, регуляторика
- **Point 3**: Supply Chain — Q2–Q3 2027 | Консолидация в одну сеть, цель снижения издержек 15–20%
- **Callout Bar**: Совокупные инвестиции: $12M за 18 месяцев; окупаемость 24 месяца
- **Source**: Оценки команды по планированию внедрения
```

### Metrics (metric-row with points)

```markdown
## Slide 6 — Performance Dashboard
- **Role**: metrics
- **Layout**: metric-row (3)
- **Eyebrow**: KEY METRICS
- **Title**: Три показателя подтверждают: enterprise-тезис работает
- **Point 1**: Enterprise ARR — $4.2M (+34% YoY)
- **Point 2**: Net Revenue Retention — 118% (+6 п.п. к прошлому году)
- **Point 3**: Enterprise Churn — 4.2% (−1.8 п.п. к прошлому году)
- **Source**: Финансовые данные FY2025
```

### Section Divider

```markdown
## Slide 7 — Section Break
- **Role**: section-divider
- **Layout**: hero
- **Eyebrow**: PART TWO
- **Hero Title**:
  - "Рыночные"
  - "возможности"
```

### Closing

```markdown
## Slide 8 — Closing
- **Role**: closing
- **Layout**: hero
- **Eyebrow**: NEXT STEPS
- **Hero Title**:
  - "Готовы"
  - "двигаться вперёд"
- **Body Text**: Контакт: team@company.com | Следующая сессия: апрель 2026
```

## Правила формата

1. **Горизонтальные линии (`---`) между слайдами** — чёткие визуальные границы
2. **Нумерация слайдов последовательная** — `## Slide 1`, `## Slide 2` и т. д.
3. **Короткий лейбл после номера** — `## Slide 3 — Enterprise Drives Revenue`
4. **Текст дословный** — сборщик копирует точно, без перефразирования
5. **Без визуальных или форматных инструкций** — никаких цветов, иконок, типов визуализации, размеров шрифта, CSS, HTML или координат сетки
6. **Без ярлыков фреймворка как заголовков** — «Situation», «Complication», «Resolution» не появляются
7. **Multi-col и metric-row указывают количество** — `multi-col (3)`, `metric-row (4)`
8. **Формат Body Text** — обычный текст для абзацев; суффикс `(bullets):` со списком, элементы с префиксом `- `
9. **Source опционален** — указывай на любом слайде с количественными утверждениями; пропускай на cover, divider, closing
10. **Значения данных встроены** — числа, проценты и тренды естественно встраиваются в текст точек, без подсказок рендеринга (бар vs. донат vs. прогресс — выбирает сборщик)
11. **Под-точки опциональны** — `Point 1` может быть одной строкой или иметь вложенные под-точки

## Анти-паттерны

| Нельзя | Почему | Делай так |
|-------|-----|------------|
| Указывать цвета (`red`, `teal`, `#FF0000`) | Сборщик подбирает цвета из темы | Просто давай контент |
| Указывать тип визуализации (`progress-bar`, `donut`) | Сборщик решает, как рендерить данные | Давай значение и подпись |
| Добавлять имена иконок или цвета бэйджей | Визуальная подача — задача сборщика | Описывай контент семантически |
| Указывать размеры или гарнитуры шрифтов | Темой управляет типографика | Опускай — сборщик применяет тему |
| Добавлять CSS или HTML | Спецификация — это контент, не код | Используй только имена полей |
| Тематические ярлыки в заголовках | Нарушает правило action-title | Пиши полные предложения с инсайтом |
| Писать абзацы прозы в Body Text | Слайдам нужен структурный контент | Используй буллиты или короткие утверждения |
| Повторять контент между слайдами | Одно сообщение на слайд | Уноси детали в приложение |
| Добавлять инструкции по переходам/анимациям | Сборщик управляет переходами | Опускай — сборщик решает |
| Добавлять поле `**Visual**` или per-slide визуальное направление | Визуальные решения — задача сборщика, он выводит из роли + контента | Опускай — описывай только что сообщить |

## Что выводит сборщик

Сборщик дека использует **role**, **layout** и **структуру точек** спецификации для самостоятельного выбора визуализации:

- **Role** → главный семантический сигнал. `argument` → карточки или колонки, `comparison` → панели рядом, `roadmap` → таймлайн-узлы, `metrics` → метрик-блоки, `framework` → опоры или step-flow. Сборщик выбирает лучшую визуальную подачу под роль.
- **Кол-во точек + Layout** → определяет сетку. `multi-col (3)` с 3 точками → три колонки. `split` с 2 точками → левая/правая панели.
- **Текст точки** → сборщик парсит контент семантически. Числа и проценты становятся выделенными метриками. Сегменты, разделённые пайпом (`Q2-Q3 2026 | description`), становятся структурированными полями. Под-точки становятся деталями внутри визуального элемента.
- **Hero Title строки** → сборщик применяет акцент / эмфазис согласно теме
- **Контраст фона** → сборщик решает светлый/тёмный по роли и теме. Cover, section-divider, closing по умолчанию тёмные; контентные слайды — светлые. Тема может переопределить.

Автору спецификации никогда не нужно думать о визуальном рендеринге. Пиши контент как нумерованные точки; сборщик выведет карточки, панели, таймлайн-узлы, метрик-блоки или любую другую визуализацию из роли и контента.

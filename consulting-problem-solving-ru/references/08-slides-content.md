# Шаг 8 — трек слайдов: правила контента

Правила контента для сборки деков. Читай этот файл после Gate 2 (скептическое ревью пройдено) и до дистилляции спецификации контента (Gate 2b).

Главный принцип: **никаких неструктурированных стен текста.** Слайды могут быть плотными, когда контент того требует — детальные дорожные карты, сравнительные таблицы, разборы фреймворков. Но каждый кусочек текста на слайде должен быть структурирован, сканируем и заслужить место. Если контент читается как абзацы прозы — он принадлежит вертикальному треку.

---

## Правило action-title

Каждый заголовок слайда — **полное предложение, формулирующее ключевой инсайт**. Веди аргументом, а не темой или цифрой.

| Плохо (тематический ярлык) | Плохо (от цифры) | Хорошо (от инсайта) |
|---|---|---|
| «Анализ рынка» | «$4.2B TAM при 23% CAGR» | «Целевой рынок достаточно большой и растёт быстро, чтобы поддержать тезис» |
| «Структура издержек» | «Издержки +18% YoY» | «Растущие издержки сжимают маржу — нужен структурный ответ» |
| «Сегменты клиентов» | «Enterprise = 62% выручки» | «Enterprise-клиенты дают большую часть выручки и всю маржу» |
| «Конкурентный ландшафт» | «5 крупных конкурентов» | «Никто из инкумбентов не закрыл рынок — окно открыто» |

**Тест**: закрой тело слайда. Заголовок один говорит тезис? Если нет — переписывай.

## Правила тела слайда

Тело — это контент под action-title. Здесь живёт «стена текста». Разные типы слайдов нуждаются в разной структуре, но у всех одно правило: **никаких неструктурированных блоков прозы.**

### Универсальное правило

**На слайдах нет абзацев.** Если текст течёт сплошной прозой — предложения, цепляющиеся за предложения — его не прочитают. Каждый кусочек контента должен быть в структурной форме: буллиты, ячейки таблицы, callout-боксы, подписанные элементы диаграммы или короткие самостоятельные утверждения. Читатель должен мочь зайти в слайд в любой точке и понять отдельные кусочки без последовательного чтения.

### Типы слайдов и их правила контента

**Argument-слайды** (самые частые — формулируют один тезис с доказательствами):
- 3–5 буллитов, каждый в одну строку (~12 слов / ~60 символов)
- Параллельная конструкция: все буллиты начинаются с одной части речи

**Comparison / evaluation-слайды** (опции, критерии, трейдоффы):
- Таблица или матрица — структура из строк и колонок
- Может быть плотной — 6–8 строк нормально, если ячейки коротки (2–5 слов)
- Помечай рекомендованную опцию в контенте (например, жирный лейбл, `→ Рекомендуется`)

**Roadmap / timeline-слайды** (фазированное внедрение, вехи):
- Контент структурирован по фазам — визуальный формат выбирает сборщик
- Каждая фаза: имя + 2–3 ключевых действия + сроки + ответственный
- Контента больше, чем на argument-слайдах — допустимо, потому что он пространственно организован

**Framework / architecture-слайды** (опоры, операционная модель, цепочка ценности):
- На основе элементов: короткие подписанные пункты (3–8 слов) по категориям или иерархии
- Может быть много элементов, если логическая группировка ясна

**Deep-dive / detail-слайды** (поддерживают фреймворк или обзорный слайд):
- Текста больше, чем на argument-слайдах — до 6–8 структурированных пунктов
- Используй под-секции с жирными заголовками для сканируемости
- Часто связаны с обзорным слайдом нумерацией (см. «Сквозная нумерация Framework→Deep-Dive»)

**Exec summary-слайды**:
- 3–5 чётких буллитов — этот слайд должен оставаться плотным независимо ни от чего
- См. отдельную секцию ниже

### Карта тип сообщения → форма представления

Когда дистиллируешь контент, тип сообщения подсказывает форму. Сборщик-скил выбирает конкретный визуал, но ты в спецификации помечаешь намерение.

| Тип сообщения | Естественная форма | Примеры |
|---|---|---|
| Изменение во времени | Линия / столбцы | LFL по кварталам, рост ARR, динамика маржи |
| Часть-целое | Водопад / стэк | Декомпозиция падения выручки, структура издержек |
| Сравнение опций | Таблица / матрица 2×2 | Build vs. Buy vs. Partner, оценка кандидатов |
| Концентрация / распределение | Парето / scatter | 20% точек дают 80% падения, кластеры по LFL |
| Последовательность шагов | Roadmap / timeline | Дорожная карта внедрения, фазы трансформации |
| Архитектура / отношения | Диаграмма блоков | Операционная модель, цепочка ценности |

Если сообщение не ложится ни в одну форму — оно слишком сложное для одного слайда. Раздели или вырази буллитами.

### Что превращает текст в «стену»

Проблема не в плотности — в отсутствии структуры. Слайд с 8 короткими пунктами в хорошо организованной таблице читаем. Слайд с 3 длинными буллитами по 2–3 строки — нет. Следи за:

- **Буллиты длиннее одной строки**: либо режь слова, либо разделяй на два пункта
- **Буллиты, которые на самом деле абзацы**: буллит с подпридаточными («которое..., приводит к..., тем самым...») — это проза с точкой впереди
- **Отсутствие визуальной структуры**: если весь контент — один сплошной список буллитов, добавь иерархию: жирные ввод, группирующие заголовки или конвертируй в другой формат (таблица, колонки, диаграмма)
- **Прелюдии**: «На основе нашего анализа...» / «Стоит отметить, что...» — начинай с тезиса

### Форматы буллитов по типу контента

**Рекомендации** — императивный глагол + объект + квантифицированный эффект:
```
• Запустить enterprise-продажи — цель $2M ARR за 12 месяцев
• Свести три региональные цепочки в одну сеть — снижение издержек 15–20%
• Нанять VP Engineering к Q2, чтобы разблокировать платформенный rebuild
```

**Выводы / инсайты** — декларативное утверждение + опорные доказательства:
```
• Enterprise-клиенты уходят вдвое реже SMB (4% vs. 9% в год)
• У топ-3 конкурентов нет присутствия в APAC — гринфилд
• Стоимость привлечения выросла на 40% за 18 мес, обгоняя рост LTV
```

**Действия / следующие шаги** — императивный глагол + ответственный + сроки:
```
• Финализировать шорт-лист поставщиков (Закупки, до 15 марта)
• Презентовать бизнес-кейс совету (CFO, апрельский совет)
• Запустить пилот фазы 1 в Северо-Западном регионе (Ops-лид, Q2)
```

### Хорошие vs. плохие примеры

| Плохо (свалка прозы) | Хорошо (дистиллированный буллит) |
|---|---|
| «Компании следует рассмотреть консолидацию трёх региональных цепочек поставок в единую интегрированную сеть, что, по нашему анализу, могло бы снизить логистические издержки на 15–20% и улучшить сроки доставки.» | **Свести три региональные цепочки в одну сеть** — снижение логистических издержек 15–20%, быстрее доставка |
| «На основе нашего анализа сегментов клиентов, enterprise-сегмент демонстрирует наивысшую готовность платить и наименьший отток, что предполагает смещение GTM-фокуса в enterprise.» | **Сместить фокус GTM в enterprise** — высший WTP, низший отток, в 3 раза LTV vs. SMB |
| «Существует значительная возможность экспансии в APAC, учитывая, что ни один из топ-3 конкурентов не имеет значимого присутствия в регионе.» | **Выйти в APAC раньше конкурентов** — у топ-3 нет регионального присутствия |
| «Внедрение должно быть фазировано в три этапа, начиная с быстрых побед в первом квартале, далее крупные оргизменения в месяцах 3–12 и структурное развитие компетенций в годах 1–3.» | **Фазируй в 3 этапа**: быстрые победы (Q1) → оргизменения (М3–12) → развитие компетенций (Г1–3) |

## Процесс дистилляции контента

Между утверждённым сторибордом (Gate 1) и сборкой HTML (Gate 4) дистиллируй весь контент с шагов 6–7 в форму, готовую к слайдам. Это отдельный шаг — не пропускай.

### Процесс

1. **Для каждого слайда в последовательности хедлайнов** определи исходный материал из шагов 6–7.
2. **Определи роль слайда** (argument, comparison, roadmap, framework, deep-dive) — она определяет правила контента и визуальный выбор сборщика.
3. **Сруби всю связующую прозу**: убирай «На основе нашего анализа...», «Это предполагает, что...», «Стоит отметить...», «Как обсуждалось в...». Начинай с тезиса.
4. **Структурируй контент** под выбранный тип слайда: буллиты для argument, таблица/матрица для сравнений, пространственный лэйаут для roadmap/framework.
5. **Применяй wall-of-text-тест**: можно ли войти в слайд в любой точке и понять отдельные кусочки? Если приходится читать сверху вниз, как документ, — переструктурируй.

### Что вырезается

- Хеджирующий язык («представляется, что», «потенциально», «можно утверждать»)
- Прелюдии («Чтобы понять X, нам сначала нужно...»)
- Избыточные доказательства (оставь сильнейшую точку, остальное вырежь)
- Квалификаторы, не меняющие тезис («в большинстве случаев», «в целом»)
- Атрибуции внутри буллитов («согласно нашему анализу») — слайд И ЕСТЬ анализ

### Куда уходит вырезанный контент

- **Слайды приложения**: поддерживающие данные, детальные разбивки, методология
- **Speaker notes**: нюансы, оговорки, переходы, разъяснения, которые презентующий говорит вслух
- **Вертикальный документ**: если пользователю нужны оба формата, документ несёт полный нарратив

## Executive Summary (формат слайдов)

Exec summary-слайд — это **3–5 чётких буллитов**, не абзацы. Следует тем же правилам, что и контентные слайды.

Адаптируется под нарративную структуру, но **никогда не использует ярлыки фреймворка**:
- **Answer-First**: рекомендация → опорные причины → эффект (буллитами)
- **Evidence-First**: ключевые сигналы → вывод, на который указывают (буллитами)
- **SCR**: контекст → нарушение → путь вперёд (буллитами, без «Situation»/«Complication»/«Resolution»)
- **Transformation**: сегодня → цель → путь (буллитами)
- **Comparative**: решение → опции → победитель → почему (буллитами)
- **Sequential**: фазы → таймлайн → результат (буллитами)

**Spine-тест**: буллиты exec summary в одиночку должны передавать весь аргумент. Заголовки слайдов в одиночку должны реконструировать exec summary.

**Пример SCR exec summary-слайда** (3 буллита, без ярлыков):

> • Сеть удерживала маржу 14% при двузначном росте до 2024
> • LFL падает 8 кварталов подряд; общесетевая лояльность не сработала — 23% точек дают 60% падения
> • Сегментная игра по точкам (закрытия + апгрейд + поддержка) возвращает LFL в плюс к Q4'27 при маржи 16%

---

## Сначала нарратив, не данные

**Это thought leadership-материал, не количественный исследовательский отчёт.** Каждый слайд должен иметь смысл без чисел. Цифры подчёркивают тезисы — не строят их.

- **Strip-тест**: убери все числа со слайда. Если он становится бессмысленным — слайд структурирован неверно, переписывай вокруг инсайта.
- **Эмфазис, не каркас**: Хорошо: «Принятие ускоряется — enterprise-внедрения утроились за год.» Плохо: «Enterprise-внедрения AI достигли 14 200 в 2024, выросли с 4 700 в 2023.»
- **Без свалок данных**: если на слайде больше 2–3 чисел, пересмотри, тянет ли каждое свой вес.

Правила целостности данных (свежесть, перекрёстная проверка, меньше — лучше) принудительно применяются на шаге 5 — см. `05-analyze.md` секция «Качество и согласованность данных». Скептический ревью-сабагент (Gate 2) поймает то, что проскользнёт.

## Структурная композиция

### Одно сообщение на слайд

Если ты не можешь сформулировать тезис слайда одним предложением (action-title) — слайд делает слишком много.

### Футер с источником

Любой слайд с числами получает строку `Источник: [цитата(ы)]` внизу (~8pt, светло-серый). Несколько источников — через точку с запятой. Без надстрочных сносок. Опускай только на слайдах без количественного контента.

### Сквозная нумерация Framework→Deep-Dive

Когда фреймворк-слайд имеет несколько блоков, а следующие слайды разбирают каждый — используй согласованную нумерацию (арабскую, римскую или буквы) и на обзорном слайде, и на детальных.

## Сборка сториборда

1. Выбери плейбук и собери последовательность слайдов согласно `08-communicate.md` (порядок сборки + выборы Q3–Q6)
2. **Narrative-first-тест**: прочитай только заголовки — они должны рассказать всю историю как логический аргумент. Если какой-то заголовок работает только из-за числа, перепиши, чтобы вёл инсайтом.
3. **Проход по числам**: только после фиксации нарратива решай, где конкретное число усилит тезис. Большинство слайдов должны работать без чисел.
4. **Проход дистилляции**: для каждого слайда дистиллируй исходники с шагов 6–7 в нужную структурную форму. Сруби связующую прозу. Применяй wall-of-text-тест.

## Ловушки (специфичные для слайдов)

- **Проза под видом буллитов**: буллит, который — полное предложение с подпридаточными, это просто абзац с точкой впереди. Режь.
- **Несогласованная структура буллитов**: если буллит 1 начинается с глагола, а буллит 3 — с существительного, слайд выглядит небрежно. Выбери одну структуру и держись.
- **Один тип слайдов везде**: дек из 15 argument-слайдов с 4 буллитами — монотонно. Меняй типы — argument, сравнительная таблица, roadmap, framework, метрика-выноска — для визуального и структурного разнообразия.
- **Слишком много слайдов на один тезис**: один аргумент = один слайд. Если ты тратишь 3 слайда на одну поддерживающую рекомендацию — консолидируй, иначе дек распухает.
- **Избегание приложения**: приложение существует не зря. Тяжёлый по деталям контент (методология, полные таблицы, чувствительности) — туда, а не в контентные слайды.
- **Плотность без структуры**: плотный слайд нормален, если контент организован (таблицы, секции с подписями, сгруппированные элементы). Плотный слайд нечитаем, если это плоский список из 10+ неразличимых буллитов.

## Сохранение спецификации (Gate 2b)

После завершения дистилляции сохрани результат как **файл контента слайдов**. Этот файл становится единственным источником истины для всей генерации дека.

### Процесс

1. **Дистиллируй все слайды** по процессу выше — у каждого слайда финализированы action-title, контентные поля и выбор лэйаута.
2. **Прочитай определение формата**: `references/08-slide-content-format.md` — там точная схема, имена полей, маппинг примитивов и правила.
3. **Запиши файл спецификации** в `{engagement_folder}/08-slide-content.md`, точно следуя определению формата.
4. **Покажи спецификацию пользователю** на ревью. Пройди по контенту каждого слайда. Пользователь утверждает, просит правки или отклоняет.
5. **Правь до явного утверждения.** Утверждённая спецификация — финальный выход скила для трека слайдов.

### Что фиксирует спецификация

- Роль и лэйаут каждого слайда
- Каждое контентное поле (eyebrow, title, body text, нумерованные точки с опциональными под-точками и т. д.)
- Значения данных, естественно встроенные в текст точек
- Цитаты источников
- Порядок слайдов

### Что спецификация НЕ фиксирует

- Визуальный стиль, бренд, тему, цвета сверх именованных семантических
- CSS, HTML, координаты сетки, гарнитуры
- Переходы, анимации
- Это всё уходит сборщику ниже по конвейеру — не этому скилу
